How this page works

A data platform light enough to fit inside a web page.

There's no server doing this. No database, no API behind a login, nothing running that I have to keep alive.

Every morning a GitHub Action runs a small dlt → dbt → DuckDB pipeline — extract, model, test — and commits one Parquet file plus the JSON this page draws. The site is static, served from Cloudflare's edge; the pipeline, its models and its run logs are all public in the repo. And when you press Run up there, that Parquet loads into DuckDB compiled to WebAssembly and every chart query executes right here, in your browser. My heavier, private services run on my own Hetzner box behind WireGuard. Right tool, right weight, for each job.

Don't take my word for it — the data is a public endpoint. Query this site from your own terminal:
duckdb -c "SELECT tool, value AS stars
FROM read_parquet('https://rensevanderzee.nl/data/metrics.parquet')
WHERE mart = 'stars_current' ORDER BY stars DESC;"
About

I'm the data engineer at Winparts, a fast-growing European car-parts retailer, where I build and maintain the data platform on Google Cloud, currently as its only engineer. dlt for extraction, dbt for modelling — both in containers — with BigQuery as the warehouse and Power BI on top. Lately I've been extending it with AI: an LLM that annotates the free text on product returns.

Before Winparts I spent three years at Sogeti — the first at Aegon as a test analyst, then two years as a data engineer, full time in the mortgage domain, on the migration from Aegon to a.s.r. On the a.s.r. side I helped build the Azure data platform: Data Factory and Synapse on Spark, into Azure SQL and a data lake. My own focus was the migration's control framework.

The AI work is the part I find most interesting at the moment — working out where an LLM actually earns its place in a pipeline, and where it just adds a moving part.

How I work
01

Right-sized, not rebuilt

Most workloads don't need a cluster. DuckDB, Parquet and a single box go a long way — and when you do outgrow them, a managed warehouse like BigQuery is the obvious next step. Right-sizing is the skill.

02

Pipelines in CI, not on call

Scheduled jobs belong in version control and CI, where they're reviewable and reproducible — not on a server someone has to remember to check.

03

Numbers you can defend

I came to engineering from testing, and it stuck. Tests in dbt, reconciliation between source and mart, and a straight answer when two reports disagree. A pipeline that runs is not the same as a pipeline that's right.
